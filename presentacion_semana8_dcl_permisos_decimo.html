📓 Sección 1

Cuentas y niveles de privilegio

Una cuenta de MySQL es 'usuario'@'host': localhost = el mismo computador · % = cualquier equipo. En el curso usamos @'localhost'.

Pulsa cada nivel: cuanto más pequeño, más preciso es el permiso.

📓 Sección 2 · Gestión de usuarios

  
Crear, revisar y borrar usuarios

  

    
CREATE USER 'usr_consulta'@'localhost'
  IDENTIFIED BY 'Consulta#2026';

SELECT user, host, account_locked
FROM mysql.user
WHERE user = 'usr_consulta';

SHOW GRANTS FOR 'usr_consulta'@'localhost';

ALTER USER 'usuario'@'localhost' IDENTIFIED BY 'nueva';
DROP USER  'usuario'@'localhost';

    

      
mysql.user
        
userhostaccount_locked

        
usr_consultalocalhostN

      

      
SHOW GRANTS · 1 fila
        
Grants for usr_consulta@localhost

        
GRANT USAGE ON *.* TO `usr_consulta`@`localhost`

      

      
USAGE = ningún privilegio: puede conectarse, nada más. Un usuario nuevo empieza así.

    

  







  
📓 Secciones 3 y 4 · GRANT, REVOKE, columnas

  
Dar y quitar privilegios

  

  

    

      
GRANT SELECT ON pulsofit.entrenadores TO 'usr_consulta'@'localhost';
GRANT SELECT ON pulsofit.planes       TO 'usr_consulta'@'localhost';
SHOW GRANTS FOR 'usr_consulta'@'localhost';

      
3 filas: USAGE + una fila por tabla
        
Grants for usr_consulta@localhost

        
GRANT USAGE ON *.* TO `usr_consulta`@`localhost`

        
GRANT SELECT ON `pulsofit`.`entrenadores` TO `usr_consulta`@`localhost`

        
GRANT SELECT ON `pulsofit`.`planes` TO `usr_consulta`@`localhost`

      

    

    

      
REVOKE SELECT ON pulsofit.entrenadores FROM 'usr_consulta'@'localhost';
REVOKE SELECT ON pulsofit.planes       FROM 'usr_consulta'@'localhost';
SHOW GRANTS FOR 'usr_consulta'@'localhost';   -- 1 fila: USAGE

      
GRANT … TO da · REVOKE … FROM quita. REVOKE no borra el usuario: solo le quita permisos.

    

    

      
GRANT SELECT ON pulsofit.entrenadores TO 'usr_consulta'@'localhost';
GRANT UPDATE (telefono) ON pulsofit.entrenadores TO 'usr_consulta'@'localhost';
SHOW GRANTS FOR 'usr_consulta'@'localhost';

      
2 filas: MySQL junta los privilegios de la misma tabla
        
Grants for usr_consulta@localhost

        
GRANT USAGE ON *.* TO `usr_consulta`@`localhost`

        
GRANT SELECT, UPDATE (`telefono`) ON `pulsofit`.`entrenadores` TO `usr_consulta`@`localhost`

      

      
Solo puede cambiar el teléfono. Y necesita SELECT: el UPDATE … WHERE id = 2 tiene que leer id.

    

  







  
📓 Sección 5 · Roles

  
Un rol es un paquete de privilegios

  

    
Privilegios
SELECT · entrenadoresSELECT · planesUPDATE (telefono) · entrenadores

    
GRANT … TO
→

    
Rol
rol_consulta

    
GRANT rol TO
→

    
Usuarios
usr_consultaotro usuario…

  

  

  

    
CREATE ROLE 'rol_consulta';
El rol se guarda en mysql.user con host % y account_locked = Y: nadie inicia sesión con un rol.

    
GRANT SELECT ON pulsofit.entrenadores TO 'rol_consulta';
GRANT SELECT ON pulsofit.planes       TO 'rol_consulta';
GRANT UPDATE (telefono) ON pulsofit.entrenadores TO 'rol_consulta';

    
GRANT 'rol_consulta' TO 'usr_consulta'@'localhost';
Si mañana cambian los permisos del rol, cambian para todos los usuarios que lo tienen.

    
SET DEFAULT ROLE 'rol_consulta' TO 'usr_consulta'@'localhost';
¡No lo olvides! Sin este paso el rol queda apagado: CURRENT_ROLE() devuelve NONE y el usuario no ve nada (error 1044 al conectarse con schema pulsofit).

    
SHOW GRANTS FOR 'rol_consulta';                              -- privilegios del rol
SHOW GRANTS FOR 'usr_consulta'@'localhost';                  -- el usuario tiene el rol
SHOW GRANTS FOR 'usr_consulta'@'localhost' USING 'rol_consulta';  -- lo que recibe

📓 Sección 6 · Tabla de errores de permisos

  
Leer el error es leer la evidencia

  

    
CódigoQué significaQué hacer

    
1142Sin ese privilegio sobre esa tablaCorrecto si el perfil no debe hacerlo; si debe, GRANT desde root

    
1143Sin ese privilegio sobre esa columnaIgual que 1142, a nivel de columna

    
1044Ningún privilegio activo en esa base (¿falta SET DEFAULT ROLE?)Revisar SHOW GRANTS y el rol por defecto

    
1045Usuario o contraseña incorrectosRevisar los datos de la conexión

    
1227Falta un privilegio global (p. ej. CREATE USER)Solo root

    
1396La cuenta o el rol ya existe (o no existe, en un DROP)Revisar mysql.user

    
3523Rol desconocidoCrear primero el rol

  

  
El mensaje dice qué comando, a quién y sobre qué tabla o columna se negó.







  
Para pensar

  
¿Cuándo se nota un cambio de permisos?

  

    
REVOKE de un privilegio (al usuario o al rol)
Se aplica en la siguiente sentencia del usuario, aunque tenga la pestaña abierta.
REVOKE UPDATE (telefono) ON pulsofit.entrenadores
  FROM 'rol_consulta';

    
REVOKE de un rol al usuario
La sesión abierta conserva el rol activo. El cambio se nota cuando el usuario vuelve a iniciar sesión.
REVOKE 'rol_consulta' FROM 'usr_consulta'@'localhost';

  

  
Por eso, cuando alguien se retira: cerrar su sesión, quitar el rol y borrar la cuenta (DROP USER). Borrar el usuario no borra el rol.

📓 Sección 7 · Buenas prácticas de seguridad de acceso

  
Diez reglas para el cuaderno

  

    
1Mínimo privilegio
Solo lo que necesita para su trabajo.

    
2root no es para trabajar
Ni para el día a día ni para las aplicaciones.

    
3Una cuenta por persona
Nunca compartir usuario y contraseña.

    
4Roles por perfil
Recepción, contabilidad, gerencia…

    
5El nivel más pequeño
Columna > tabla > base. Nunca *.* a usuarios comunes.

    
6Restringir el host
@'localhost' si basta; evitar @'%'.

    
7Contraseñas seguras
Largas, difíciles de adivinar; cambiarlas con ALTER USER.

    
8Revocar a tiempo
Cambio de cargo o retiro: REVOKE / DROP USER.

    
9Revisar
SHOW GRANTS y mysql.user periódicamente.

    
10Probar
Entrar con la cuenta: lo prohibido debe dar 1142 / 1143.
